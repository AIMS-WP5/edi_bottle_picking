# cuMotion Integration Plan — WS_EDI (feature/cumotion-integration)

## Context

The four actively-developed repos (`edi_isaacsim`, `edi_ur`, `edi_bottle_picking`,
`edi_ai_moveit_servo`) are on branch `feature/cumotion-integration`. Goal: integrate NVIDIA
cuMotion (GPU-accelerated motion planning) into the MoveIt planning + trajectory-following
path used by `edi_bottle_picking` against the Isaac Sim scene, alongside the existing
OMPL and DP paths. First step: re-validate the existing sim stack on the new
`env_isaacsim6` (Isaac Sim 6.0.1 GA) — an untested combination.

**Status directory (user decision):** create `src/edi_bottle_picking/status/`; save this
plan there after approval, and after each iteration commit a status summary together with
that iteration's code changes (per-repo commits listed in each summary).

**User decisions:** planner selection via an orthogonal `--planner ompl|cumotion` flag
(not a third insertion_mode); install via a timeboxed apt probe with source-build
fallback; reuse resources from `~/work2/github/gstrazds/BT/robo-codegen-edi` (branch
`cumotion`) — a working cuMotion setup for the same robot (see Prior art).

## Key facts (verified by exploration)

- **Single code choke point:** all joint-space planning goes through
  `MoveGroupInterface::plan()` in
  `src/edi_robot_control/manipulator_interface/src/manipulator_interface.cpp`
  (`predefined_pose` L426, `pose_goal` L470, `joint_goal` L513, `plan_pose_goal` L679);
  no planner/pipeline ID is ever set. `setPlanningPipelineId()` (exists in MoveIt 2.5.x)
  routes all of them with one call. All plans re-timed by `trajectory_generation()` L104
  (TOTG). Cartesian primitives (`cartesian_goal` L576, `cartesian_descent_feasible` L735)
  use `computeCartesianPath`, which bypasses planner plugins — they stay native; cuMotion
  has no Cartesian-path support (joint goals + single EE pose goals only).
- **Single config choke point:** `src/edi_ur/edi_moveit_config/launch/edi_ur_moveit.launch.py`
  L169–235 loads one OMPL pipeline as flat params. Humble move_group supports
  `planning_pipelines: [...]` + `default_planning_pipeline` + per-pipeline nested dicts,
  expressible in this classic (non-MoveItConfigsBuilder) launch.
- **insertion_mode switch:** `conveyor_feeding_utils.cpp` L438–447 (`dp`|`moveit`); launch
  arg in `conveyor_feeding.launch.py` L40–59; validated in `bringup_sim_stack.sh` L111.
- **Execution unchanged for cuMotion:** trajectories execute via
  `joint_trajectory_controller` over `topic_based_ros2_control`
  (`/isaac_joint_commands`/`/isaac_joint_states`); Isaac only mirrors commands — no
  edi_isaacsim changes needed for execution.
- **cuMotion for ROS (Isaac ROS release-3.2, last Humble release):**
  `cumotion_planner_node` (Python; action server `cumotion/move_group` of type
  `moveit_msgs/action/MoveGroup`; params `robot:=<xrdf>`,
  `urdf_path:=<xacro-expanded URDF with <ros2_control> stripped>`; mirrors planning-scene
  world objects; ESDF/nvblox optional, off by default) + MoveIt plugin
  `isaac_ros_cumotion_moveit/CumotionPlanner` configured by NVIDIA's shipped
  `isaac_ros_cumotion_planning.yaml`. NVIDIA also ships `ur5e.xrdf` (format 1.0) in
  `isaac_ros_cumotion_robot_description`. Only ONE move_group / one cumotion node
  instance allowed (concurrent goals → CUDA errors).
- **Host (verified):** RTX 5090 (Blackwell sm_120), driver 595.71.05. `/usr/bin/python3`
  (3.10) already has torch 2.7.1+cu128 with CUDA working on sm_120; nvcc 12.8 +
  cuda-12.8/13.0 installed → source build fully provisioned. NVIDIA isaac apt repo NOT
  yet configured. MoveIt is binary apt 2.5.9 (only moveit_task_constructor vendored) —
  source-building `isaac_ros_cumotion_moveit` removes the known ABI risk (issue #27).
  Shell default python is env_isaacsim6 (py3.12) — all probes/builds must pin
  `/usr/bin/python3` with conda deactivated.

## Prior art: robo-codegen-edi (~/work2/github/gstrazds/BT/robo-codegen-edi, branch `cumotion`)

Working cuMotion setup for the same UR5e + Schmalz ECBPi vacuum tool, but on Isaac Sim's
**built-in** `isaacsim.robot_motion.cumotion` extension inside Isaac's py3.12, executing
directly on the articulation — its execution path does NOT carry over to ROS/MoveIt; the
descriptions, measurements, assets, and planning-call patterns DO:

- **XRDF + collision spheres:** `robot_configs/ur5e_cumotion/robot.xrdf` (XRDF format
  2.0, generated by `utility_scripts/generate_ur5e_cumotion_config.py`): 39 spheres on
  arm links (none on the vacuum tool), accel 12 / jerk 500 (deliberately conservative;
  README documents why), `tool_frames: [tool0]`, `default_joint_positions` =
  EDI_DEFAULT_Q. Use as the seed for our XRDF; check format 2.0 vs the 1.0 spec that
  isaac_ros_cumotion release-3.2 parses — fall back to NVIDIA's `ur5e.xrdf` as the base
  and port spheres/limits/default-q if needed.
- **Corrected vacuum-tool length:** `TOOL_TIP_LENGTH = 0.3013` m from tool0 flange to
  suction-cup tip, along tool0 +Z (`ur5e_common.py` L32; verified two independent ways
  2026-07-12; history 0.320 → 0.306 → 0.3013; some docs stale at 0.306/0.32 — the code
  constant is authoritative). **Reconciliation required:** WS_EDI's `virtual_ee_link` is
  0.24045 m past tool0 — a different reference point (interface frame vs physical tip),
  and all `moveit_insert_*` offsets are calibrated around it. Do NOT blindly change it.
- **Fixed-collision USD assets:** `SimEnvs/assets/madara_pad.usd` + `m_pad_{RED,GREEN,
  BLUE,BLACK}.usd` — commit `38341be` replaced the lumpy convexDecomposition with 19
  accurate invisible collision boxes (socket ring apothem 0.0215, floor at measured
  0.039), original mass pinned; tooling in `utility_scripts/fix_pad_collision.py` +
  `measure_pad_socket.py`. Bottle collision fixes in `2990d93`, propagated in
  `63403b8`/`aa6de1b`. Candidates to port into the edi_isaacsim scene.
- **Planning-call patterns** (`robot_controllers/cumotion_commander.py`): pose goal →
  cuMotion `CollisionFreeIkSolver` seeded at current config → c-space goal in the current
  IK basin, with a basin-flip guard (Δjoint > π rejected); planner-only collision world
  with the held item excluded (`cumotion_plan_world.py`). This validates our existing
  seeded-IK (`/compute_ik` → `joint_goal`) insertion approach — prefer joint-space goals
  to cumotion_planner_node too. Migration diary in `status/cumotion-migration/00..11` +
  `docs/complex-motion-planning-recipe.md` — read before iterations 4–6.
- **Probe scripts:** `utility_scripts/probe_cumotion_{,ik_,planner_}ur5e.py` — patterns
  for our standalone smoke tests (Isaac-side; ours will target the ROS action server).

## Design decisions

- **D1 install:** timeboxed (~30 min) apt probe (`ros-humble-isaac-ros-cumotion{,-moveit,-robot-description}`
  from `deb https://isaac.download.nvidia.com/isaac-ros/release-3 jammy release-3.0`);
  expected failure mode "no kernel image for sm_120" → purge and source-build
  `isaac_ros_cumotion` @ release-3.2 (with curobo_core submodule; CUDA extensions compile
  at colcon-build time, `TORCH_CUDA_ARCH_LIST="12.0+PTX"`, nvcc 12.8) into this workspace,
  plus vendored `nvblox_msgs` (import dependency, msgs-only).
- **D2 selection:** new ROS param `planning_pipeline` (default `"ompl"`) on
  manipulator_interface, set once via `setPlanningPipelineId()`; threaded through
  `conveyor_feeding.launch.py` and a new `--planner ompl|cumotion` bringup flag.
  insertion_mode stays `dp|moveit` (orthogonal axes; cuMotion then services ALL
  joint-space moves — pick, transfer, above-socket — in either mode).
- **D3 XRDF:** seed from robo-codegen-edi `robot.xrdf` (spheres/limits/default-q), in the
  format isaac_ros_cumotion 3.2 accepts (fall back to NVIDIA `ur5e.xrdf` base if format
  2.0 is rejected) → `edi_moveit_config/config/cumotion/edi_ur5e.xrdf`; set
  `tool_frames: ["virtual_ee_link"]` (manipulator_interface targets
  `getEndEffectorLink()` = `virtual_ee_link`; wrong frame = 24 cm pose error); add
  collision spheres for the vacuum tool (robo-codegen has none — clearance there only
  protected arm links; sphere geometry from `schmalz_vacuum.xacro` + the measured
  0.3013 m tip length).
- **D4 stripped URDF:** launch-time generation via new
  `edi_moveit_config/scripts/generate_cumotion_urdf.py` (xacro python API + strip
  `<ros2_control>` elements → cache path), invoked by the cumotion launch file so it never
  drifts from the live robot_description (robo-codegen's generator script is the model,
  but ours must keep our URDF's real kinematics incl. `virtual_ee_link`).
- **D5 node ownership:** new `edi_moveit_config/launch/cumotion_planner.launch.py` runs
  the generator + `cumotion_planner_node`; bringup adds a tmux window `cumotion` only
  when `--planner cumotion`.
- **D6 re-timing:** keep TOTG re-timing for cuMotion plans initially (preserves the
  sim-gated 0.2 scaling; path unchanged), but skip waypoint-count gating for dense
  (dt=0.025) cuMotion trajectories; add `retime_plans` param (default true) for A/B of
  native cuMotion timing (`time_dilation_factor`) in the comparison iteration.
- **D7 move_group config:** convert flat OMPL params → multi-pipeline
  (`planning_pipelines`/`default_planning_pipeline`, OMPL default); `use_cumotion:=false`
  launch arg gates loading the cumotion pipeline, so the stack is unchanged (and works
  pre-install) unless explicitly requested.
- **D8 scene assets:** adopt robo-codegen-edi's fixed-collision pad (and bottle) USDs into
  the edi_isaacsim scene as their own iteration with before/after placement-accuracy
  comparison (they change contact physics, so they must not be conflated with the
  planner comparison). Tool-length reconciliation (0.3013 vs virtual_ee_link 0.24045) is
  an explicit investigation with a decision gate — changing it shifts every calibrated
  `moveit_insert_*` offset.

## Iterations

Each iteration: state repos touched, verify, write
`src/edi_bottle_picking/status/iteration-NN-<slug>.md`, commit status with code per repo.
Isaac started manually first (`python simplified_ur5_scene.py --omnigraph`, env_isaacsim6).
cuMotion is strictly additive/opt-in — OMPL/DP behavior preserved throughout.

### 0 — Baseline re-validation on Isaac Sim 6.0.1 (env_isaacsim6)
Repos: edi_bottle_picking (status/ dir + plan copy + baseline doc); edi_isaacsim only if
6.0.1 breaks the scene.
Run: dp mode (`bringup_sim_stack.sh --no-debug --bottle-picking-iterations 5`, with
`--model saved_model_9-06-2026-rand-range` per known-good memory), then `down`; moveit
mode (`--insertion-mode moveit ...`, Isaac restarted with `--pad-adj-x 0 --pad-adj-y 0`).
Archive `/tmp/edi_sim_logs/`; record success counts + placement accuracy (existing
methodology). Verify: ≥4/5 cycles per mode or documented pre-existing failures.

### 1 — Scene asset upgrade + tool-length reconciliation (edi_isaacsim)
Repos: edi_isaacsim (assets/scene), edi_bottle_picking (status).
Steps: port fixed-collision `madara_pad.usd` (+ color variants) and fixed bottle assets
from robo-codegen-edi (or re-run its `fix_pad_collision.py` against our assets); rerun the
Iteration-0 moveit-mode runs → before/after placement accuracy. Investigate tool length:
measure our scene's tool geometry with robo-codegen's `measure_tool_tip.py` approach,
determine what `virtual_ee_link` (0.24045 m) denotes vs the 0.3013 m suction tip, and
document; only adjust URDF/scene + recalibrate `moveit_insert_*` offsets if measurements
show our current grasp/insert contact is actually wrong (decision gate — may defer).
Verify: moveit-mode success rate/accuracy ≥ baseline with fixed assets; findings doc.
Rollback: assets are per-repo commits in edi_isaacsim.

### 2 — GPU/ABI probe + install (riskiest unknown, front-loaded; no stack integration)
Repos: edi_bottle_picking (status); possibly new vendored `src/isaac_ros_cumotion` +
`nvblox_msgs`.
Steps: add NVIDIA apt repo + install cumotion packages; probe with `/usr/bin/python3`
(conda deactivated): `import curobo` + minimal MotionGen joint-goal plan on builtin ur5e
config. On sm_120 failure (expected): purge apt cumotion packages, clone release-3.2
(--recurse-submodules) + nvblox_msgs into `src/`, colcon build
`--packages-up-to isaac_ros_cumotion_moveit isaac_ros_cumotion_robot_description` with
`TORCH_CUDA_ARCH_LIST="12.0+PTX"`, re-probe. Plugin load sanity vs binary MoveIt 2.5.9.
Verify: MotionGen solves a plan on the GPU. Rollback: purge/delete — zero stack coupling.

### 3 — Robot assets: stripped-URDF generator + XRDF
Repos: edi_ur (edi_moveit_config). New: `scripts/generate_cumotion_urdf.py` (D4),
`config/cumotion/edi_ur5e.xrdf` (D3: robo-codegen spheres/limits/default-q, tool frame
`virtual_ee_link`, new vacuum-tool spheres; verify format compatibility with
isaac_ros_cumotion 3.2), install rules.
Verify: generated URDF has no `<ros2_control>` and contains `virtual_ee_link`; curobo
FK of `virtual_ee_link` at a known joint state matches tf2 (`base_link`→`virtual_ee_link`)
to ≤1e-4 m. Rollback: additive files only.

### 4 — Standalone cumotion_planner_node + smoke client (no move_group changes)
Repos: edi_ur (new `launch/cumotion_planner.launch.py`), edi_bottle_picking (new
`scripts/cumotion_smoke_test.py` — rclpy action client on `cumotion/move_group` sending a
joint goal near home + a `virtual_ee_link` pose goal; prints error code/planning
time/duration; modelled on robo-codegen's probe scripts).
Verify: with Isaac playing + control stack up, both goals SUCCEED; exactly one cumotion
node instance. Rollback: additive only.

### 5 — move_group multi-pipeline conversion (behavior-preserving)
Repos: edi_ur. File: `edi_ur_moveit.launch.py` L169–235 per D7.
Verify: `use_cumotion:=false` → rerun Iteration-0 regression, must match baseline (diff
move_group startup pipeline logs); `use_cumotion:=true` + cumotion node → RViz pipeline
dropdown shows `isaac_ros_cumotion`, one manual RViz plan executes via cuMotion.
Rollback: single-file revert.

### 6 — Client-side planner selection + TOTG gating
Repos: edi_robot_control (manipulator_interface.cpp: declare `planning_pipeline` +
`retime_plans` in `initParameters()` L30–58, call `setPlanningPipelineId()`; adjust
`trajectory_generation()` L104 gating per D6; header), edi_bottle_picking
(`conveyor_feeding.launch.py`: `planning_pipeline` arg → node param, same pattern as
`insertion_mode`). Existing seeded-IK → `joint_goal` insertion flow already matches
robo-codegen's basin-preserving pattern — keep it; cuMotion services the joint goals.
Verify: build; `planning_pipeline:=ompl` regression unchanged; `:=isaac_ros_cumotion`
(+ `use_cumotion:=true` + node) → cumotion node logs each goal; one full
pick+insert(moveit) cycle completes. Rollback: param default "ompl".

### 7 — Bringup integration (`--planner` flag)
Repos: edi_bottle_picking. File: `scripts/bringup_sim_stack.sh` — `--planner ompl|cumotion`
(validated like insertion-mode at L111); when cumotion: `use_cumotion:=true` on the moveit
window, new `cumotion` tmux window (D5), readiness poll on `ros2 action list | grep
cumotion/move_group` before the pick window, `planning_pipeline:=isaac_ros_cumotion` to
conveyor_feeding; update header help + summary echoes.
Verify: `--planner cumotion --insertion-mode moveit --no-debug
--bottle-picking-iterations 3` completes; default invocation identical to baseline;
`down` clean. Rollback: default ompl; one script.

### 8 — Validation matrix + comparison writeup
Repos: edi_bottle_picking (status), possibly edi_ur (xrdf sphere / time_dilation tuning).
Run {ompl, cumotion} × {dp, moveit} × ≥5 cycles: success rate, placement accuracy,
planning latency, trajectory duration; A/B `retime_plans=false` +
`time_dilation_factor≈0.2` vs TOTG. Explicitly test transfer-with-attached-bottle
clearance — the per-cycle `AttachedCollisionObject` on `virtual_ee_link`
(`conveyor_feeding_utils.cpp` L340) is likely invisible to cuMotion (world objects only;
robo-codegen solved this by excluding the held item from the planner world); mitigate
with padded gripper spheres, note `isaac_ros_cumotion_object_attachment` + nvblox/ESDF
as follow-ups. Verify: cumotion ≥ baseline success; tables in
`status/iteration-08-comparison.md`.

## Risk register
1. sm_120 prebuilt kernels — front-loaded to Iteration 2; source-build toolchain verified.
2. Env leakage — pin `/usr/bin/python3`, deactivate conda for all ROS builds/probes.
3. XRDF format 2.0 (robo-codegen / Isaac 6.0.1) vs 1.0 (isaac_ros_cumotion 3.2 spec) —
   checked in Iteration 3; NVIDIA `ur5e.xrdf` base is the fallback.
4. Tool-length reconciliation (0.3013 tip vs 0.24045 virtual_ee_link) — different
   reference points; decision-gated in Iteration 1; touching it shifts all calibrated
   `moveit_insert_*` offsets.
5. Attached bottle invisible to cuMotion — tracked to Iteration 8.
6. Single cumotion-node/move_group instance — bringup owns exactly one window; smoke
   tests never run alongside it.
7. Cartesian descent stays native by design — documented so nobody expects cuMotion there.
8. Fixed-collision assets change contact physics — isolated in Iteration 1 with its own
   before/after so planner comparisons (Iteration 8) aren't confounded.
